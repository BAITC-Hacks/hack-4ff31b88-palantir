# Palantir — агент прогноза ВЭС

Цикл: `fetch_weather → prepare → predict → analyze → save`, почасовой прогноз
на 48 часов с ежедневным пересчётом. Цель — нормализованная мощность станции 0–1
в соглашении модуля данных (среднее по доступным турбинам), не энергия в МВт·ч.

## Запуск с нуля

Python 3.10+, доступ к приватному репозиторию GitHub:

```bash
git clone https://github.com/BAITC-Hacks/hack-4ff31b88-palantir.git
cd hack-4ff31b88-palantir
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python run_backtest.py --demo --out runs/demo
```

Демонстрация использует синтетические числа, проверяет механику и не требует API.
Реальный архив погоды с простым бейзлайном:

```bash
python run_backtest.py --baseline --weather archive --out runs/baseline
python plot_results.py --predictions runs/baseline/february_latest.csv --out charts/baseline
```

Каждый эксперимент использует новую папку `--out`: существующая история защищена
от перезаписи. Кэш погоды используется повторно. Open-Meteo работает без ключа.
Ошибка архива не подменяется синтетическими данными.

## Структура и роли

| Файл / папка | Назначение |
|---|---|
| `data/` | История, архив погоды, признаки — Человек 1 |
| `forecast_pipeline.py` | Адаптер погодного модуля и модели |
| `agent.py` | Анализ, резюме, история версий, виртуальные часы |
| `run_backtest.py` | Единая команда запуска |
| `plot_results.py` | Графики прогноза и фактов при их наличии |
| `tests/` | Проверки анализа, календаря, интеграции и графиков |
| `docs/model_contract.md` | Интерфейс для модели Человека 2 |
| `docs/validation.md` | Проверки и оставшиеся ограничения |

Человек 2 передаёт обученную модель, функцию предсказания и метаданные.
Человек 3 соединяет модули, анализирует, запускает бэктест и сохраняет результат.
Подробности источников: [Данные и погода](data/README_data.md).

## Модель и бейзлайн

В репозитории уже есть бейзлайн Человека 2 — `model.baseline_nwp.predict`.
Полный прогон с ним:

```bash
python run_backtest.py --model model.baseline_nwp:predict --model-metadata model/baseline_metadata.json --out runs/team_baseline
```

Обученная ML-модель пока не включена. Встроенный `--baseline` — медиана исторической мощности по
бинам наблюдаемого ветра 0.5 м/с, интерполируемая по прогнозному `ens_ws100`.
Он нужен для проверки полного цикла, не заменяет LightGBM. Несовпадение высоты
и распределения наблюдаемого и прогнозного ветра ограничивает его качество.

Когда готова модель:

```bash
python run_backtest.py --model model:predict --model-metadata model_metadata.json --out runs/model
```

Модель получает результат `data.features.add_features()` без фактической мощности.
Выход — DataFrame с `target_time,power_pred` (или `power`), ровно 48 уникальных часов станции.
Отдельные пропуски признаков обрабатывает модель; полное отсутствие прогнозного
ветра отклоняет запуск. [Полный контракт](docs/model_contract.md).

## Календарь и повторный расчёт

Внутреннее время — UTC, итоговый февраль определяется по часам SCADA.
`data/processed/meta.json` сейчас задаёт **сдвиг +7 часов**. Это предположение
модуля данных по корреляции температуры, а не официальный часовой пояс Казахстана.
Нужно подтвердить его у организаторов. При изменении `--scada-offset` необходимо
согласованно пересобрать SCADA и модель, а не только изменить раннер.

При +7 виртуальные запуски идут ежедневно в 17:00 UTC:

| Запуск, UTC | Целевые часы SCADA |
|---|---|
| 31.01 17:00 | 01.02 00:00 — 02.02 23:00 |
| 01.02 17:00 | 02.02 00:00 — 03.02 23:00 |
| … | … |
| 27.02 17:00 | 28.02 00:00 — 01.03 23:00 |

Каждое значение описывает интервал `[target_time, target_time + 1 час)`.
Первый начинается в момент выпуска, последний заканчивается через 48 часов.
В истории `lead_end_hours` = 1…48, `lead_hours` = 0…47 (до начала интервала).
Готовый `test_features.parquet` собран для 00:00 UTC: раннер не выдаёт его за
прогнозы 17:00, а пересобирает признаки из архивной погоды.

Всего 28 запусков. Новый принятый пакет заменяет 24 пересекающихся часа станции.
Итог: 672 часа февраля и 648 замен (27 × 24). Мартовский хвост остаётся в истории,
но исключается из итогового февраля. Даже при одинаковых числах обновляется
дата выпуска; `changed_points` считает изменения больше `1e-9`.

## Проверки и выходные файлы

- Пропущенный час, дубликат, NaN/Inf или мощность вне 0–1: пакет отклоняется.
  0 и 1 допустимы. Нет скрытого обрезания или заполнения нулями.
- Скачок соседних часов больше 0.30: предупреждение.
- Отличие от предыдущего прогноза того же часа больше 0.15: предупреждение.
- Пороги — эвристики в долях мощности, меняются через `--jump` и `--revision`.
  Предупреждения не меняют прогноз: большой скачок может быть реальным.

При ошибке сохраняется старая версия, следующий день обрабатывается независимо.
Журнал хранит `old,new,delta`, среднюю и максимальную абсолютную разницу.
История и замена значений сохраняются одной транзакцией SQLite. База переживает
прерывание; автоматического продолжения незавершённого эксперимента пока нет.

- `february_latest.csv` / `.json`: последняя принятая версия каждого часа февраля.
- `forecast_history.csv`: численно валидные точки всех предложенных пакетов,
  дата выпуска, горизонты, флаг `accepted`.
- `runs.jsonl`: проверки, резюме, прогнозы и изменения за каждый день.
- `backtest.sqlite`: история и актуальные значения.
- `summary.json`: покрытие, успешные запуски, количество замен.

Для метрик выбери `accepted=True` в истории, отсеки март и раздели горизонты
по `lead_end_hours` 1–24 / 25–48. Итоговая последняя версия не подходит для оценки
обоих горизонтов. Код завершения 0 требует полного февраля и принятия всех запусков;
код 2 — ошибки или неполное покрытие. `--start`/`--end` позволяют проверить фрагмент,
но полнота всё равно оценивается относительно всего февраля.

## Погода и отсутствие будущих данных

`--weather archive` скачивает архив каждой модели один раз и вызывает `assemble()`
для каждого виртуального выпуска. `--weather fetch` вызывает `fetch_forecast(issue_time)`
ежедневно. Оба режима используют модуль Человека 1, `add_features()` и `check_no_leakage()`.

Журнал хранит погодные модели, `previous_dayN` и консервативные границы времени
выпуска/доступности. Это **расчётные границы**, не точные метки NWP-выпусков от API.
Доступность зависит от корректности правила выбора `previous_dayN` и принятой
задержки публикации 8 часов. [Описание Open-Meteo Previous Runs](https://open-meteo.com/en/docs/previous-runs-api).

Для модели проверяется `training_data_available_at <= issue_time`; дата должна
учитывать обучение, подбор признаков и предобработку. Правдивость метаданных
проверяется владельцем модели. Бейзлайн использует только часы с
`target_time + 1 час <= issue_time`, то есть полностью завершённые интервалы.

## LLM-резюме

Без ключа работает локальное резюме. Для LLM задай `OPENAI_API_KEY` и передай
`--llm-model` с доступной моделью. Один вызов на день. Ошибка, тайм-аут, отсутствие
SDK или пустой ответ включают локальный вариант. Отправляются только сводные числа
проверок, без исходных CSV. LLM не меняет численные значения и решение о принятии.
[Формат OpenAI Responses API](https://developers.openai.com/api/docs/guides/text).

## Факты и графики

В исходных CSV нет февраля, они заканчиваются 31 января. Поэтому точность на
феврале пока не измерена. Без `--facts` график показывает только прогноз и явно
подписывает отсутствие фактов. После получения фактов подготовь почасовой CSV:
`turbine_id,valid_time,actual_power`, где `turbine_id=station`, время с UTC-смещением.

```bash
python plot_results.py --predictions runs/model/february_latest.csv --facts facts_february.csv --out charts/model
```

Сопоставление по времени в UTC, пропуски остаются пропусками. Если совпадающих
фактов нет, скрипт выдаёт ошибку. MAE нормализованной мощности уже выражен в долях
номинала; процентные пункты = MAE × 100. Пересмотр прогноза не равен его точности.
